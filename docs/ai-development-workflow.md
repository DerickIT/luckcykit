# AI 辅助开发工作流

本文定义 AI 助手、自动化工具与协作者在 LuckyTV 中处理需求、修改代码和交付结果的统一流程。仓库根目录 `AGENTS.md` 是代码库内的强约束；本文补充如何把需求转化为可追踪、可验证的改动。若本文与用户当前明确要求冲突，以用户要求为准；不得因此绕过安全、授权或数据保护边界。

## 工作原则

1. **先核实现状，再提出方案。** 以当前代码、配置、测试、文档和运行证据为准；先检查工作区状态，阅读调用链和相邻测试，不凭历史印象改代码。
2. **以需求为边界，最小化变更。** 只修改满足需求所需的文件，不顺手重命名、格式化、升级依赖或重构无关模块。保留已有用户改动。
3. **先定数据与职责边界。** 写清状态权威来源、输入输出、错误传播、权限、持久化、异步生命周期和外部依赖。遵循 `AGENTS.md` 中的目录职责与依赖方向。
4. **验证行为，不验证实现文本。** 优先编写或运行测试验证外部行为；避免通过源码字符串、私有实现细节或已知缺陷快照锁定实现。
5. **安全和真实性优先。** 不虚报测试、构建、浏览器验收或部署结果；不把计划写成已完成，不把本地缓存写成服务端持久化成功。
6. **工具有边界。** 默认不启动开发服务器、不做发布、不提交、不推送、不清理用户数据。任何不可逆、对外可见或跨信任边界操作，先取得明确授权并遵循当前执行环境的安全策略；用户授权不能用于绕过策略拦截。

## 标准开发流程

### 1. 接收和分类需求

- 复述可验证的目标、目标用户、外部行为变化和明确不做的事；发现需求缺口时先采用安全、符合现有架构的默认值，只有会改变数据、权限、费用或兼容性时才请求决策。
- 分类为缺陷、功能、重构、文档、运维或安全变更，并评估影响面：前端、后端、桌面、数据库、外部 API、插件、部署和数据迁移。
- 非琐碎功能、跨层变更、数据结构变化、支付/身份/权限/密钥/删除等高风险工作，先补需求记录或设计决策，再实施。记录格式见 [`requirements/README.md`](requirements/README.md) 和 [`requirements/template.md`](requirements/template.md)。

### 2. 探查仓库

- 检查 `git status --short`，确认分支和已有修改；不要覆盖、暂存、撤销或清理不属于本次任务的改动。
- 搜索入口、调用方、配置、锁文件、领域合同、持久化、错误处理、相邻测试和专题文档。
- 明确唯一事实来源和业务不变量；确认变更是否触及公开 API、存储格式、迁移、插件协议或本地工作区兼容性。
- 方案应说明目标文件/模块、数据与错误流、权限边界、失败和回滚策略、需要同步的文档与验证路径。

### 3. 实施

- 先写或更新能表达需求行为的测试；测试无法覆盖的交互或部署验收，列出人工验证步骤和证据要求。
- 分层实现：UI 只协调交互；API/handler 负责协议边界；领域服务实现规则；repository 负责持久化。不要增加只透传参数的 helper 或重复计算同一业务结论。
- 持久化、权限、账务、密钥、上传、删除与外部请求采用失败显式、可审计、幂等或可恢复的设计；错误保留可操作原因，同时清除内部地址和凭据。
- 数据库变更只新增迁移版本；同步更新数据库文档。API、配置、SSE、存储、安全或部署边界变更时更新对应专题文档。
- 保持变更聚焦；不修改生成文件、依赖或锁文件，除非需求确实需要。

### 4. 验证

- 选择与改动风险相称的最小充分验证，并报告实际命令、结果、未覆盖范围和阻塞原因。详细命令遵循 `AGENTS.md` 的验证纪律。
- 失败时分析原因，不通过放宽断言、删除有意义测试或吞掉错误使验证变绿。连续三次同类失败后停止盲试，整理现象与新假设。
- UI 变更尽可能验证关键路由、交互、明暗主题、窄视口、滚动和错误/空/加载态；静态阅读不能替代浏览器验收。
- 交付前检查 `git diff --check`、变更清单、敏感信息、文档同步、工作区是否残留无关改动，以及 `AGENTS.md` 要求的结构预算。
- 后端测试若打开 SQLite 到 `t.TempDir()`，必须用 `t.Cleanup` 关闭连接（或在 `TestMain` 关闭）。Windows 上未关闭的句柄会让 `TempDir` 清理失败，整个临时目录留在 `%TEMP%`；一次全量 `go test ./...` 可泄漏数 GB。清理入口：`node scripts/clean-local-cache.mjs`（加 `--dry-run` 预览）。
- 本仓库的后端测试用 `node scripts/go-test.mjs [包或参数]` 运行：它把 `TEMP`/`TMP` 对齐到 `go env GOTMPDIR`（Go 环境目录下的 temp），避免测试临时库堆在 C 盘 `%TEMP%`。直接 `go test` 不会自动改这个变量。

### 5. 交付和需求归档

- 总结改了什么、为何这样做、影响范围、验证结果和已知限制；引用文件路径与行号。
- 只有目标行为全部满足且证据齐备时，需求记录才标记为“完成”。未验证的项明确标为未验证，不用“应该通过”。
- 需求有变更时追加变更记录和决策理由，不悄悄改写验收标准；取消或延期也记录原因及后续条件。
- 提交、推送、合并、删除远程数据或发布均是独立操作，不能从“完成开发”中推定获得授权。

## AI 生成内容与技能约束

- AI 输出是待审阅的候选修改，不是事实来源；API、依赖、SDK 和安全行为须核对本仓库实现及必要的官方资料。
- 不把用户输入、生产数据、密钥、Cookie、支付信息、工作区文件或未公开业务资料发送到未经授权的外部模型或工具。
- AI 不得自行扩大权限、执行未授权脚本、调用真实付费模型、触发真实支付/退款、删除数据、发布内容或改变远端仓库状态。
- 仓库内 `SKILL.md` 属于 LuckyTV 产品技能或插件资产，不等同于 Claude Code 的项目指令。编写产品技能时遵守 Agent Skills 格式，并明确权限、脚本执行条件、输入输出和风险；不把隐藏提示词当安全边界。
- 自动化或 Agent 操作必须经过服务端授权和业务校验；前端确认界面不能替代服务端权限检查。高影响操作需要可追踪的授权、对象范围和结果记录。

## 完成定义

一个变更只有在以下条件都满足时才可称为完成：

- 需求和验收标准明确，行为与范围一致；
- 权限、数据归属、失败语义、异步回写和安全边界完整；
- 必需测试或替代验收执行并如实报告；
- API、数据库、配置、部署及用户文档按影响同步；
- 没有引入密钥、本地数据、构建产物或无关修改；
- 需求记录状态与实际证据相符，剩余事项明确列出。
