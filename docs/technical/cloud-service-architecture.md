# 好运TV云服务架构方案

- 状态：目标架构与实施记录；当前需求见 [004 云服务生产闭环与 OneAPI 托管模型](../requirements/004-cloud-hosted-model-oneapi.md) 和 [001 微信登录与托管模型服务](../requirements/001-wechat-auth-hosted-model-service.md)。
- 当前实现仍为 loopback SQLite 开发沙箱；邮箱 OTP 可通过显式 SMTP/TLS 与 HMAC 配置启用；托管文本任务可经固定 OneAPI 数据面并按 usage 结算。独立管理员 bootstrap/session/RBAC 基础已实现，管理运营 API 与生产部署尚未完成。

## 1. 架构决策

首期采用**一个独立部署的模块化单体云服务**。账号、额度/账本、支付、模型目录和托管模型网关运行在同一个服务边界内，但按领域模块划分接口、数据写入责任和测试边界。既不把这些职责塞进桌面本地后端，也不提前拆成多个微服务。

```text
LuckyTV Desktop
  ├─ Local workspace API ──> Local Go runtime + SQLite/files
  │                           └─ BYOK providers / local plugins
  └─ Cloud API ─────────────> LuckyTV Cloud (modular monolith)
                                ├─ Identity (email OTP; WeChat not in current scope)
                                ├─ Catalog & pricing
                                ├─ Orders & payment adapters
                                ├─ Credit ledger / reservations
                                ├─ Hosted model gateway & usage
                                └─ Operations / audit
                                     ├─ Cloud relational database
                                     ├─ Sandbox payment (real payment deferred)
                                     └─ OneAPI Chat Completions data plane
```

## 2. 信任边界与身份

- **本地 workspace identity**：只表示这台安装中的本地数据所有者；维持单用户语义，不随登录变化。
- **Cloud account**：只用于云 API、云端订单和托管模型权限。不能用来选择本地项目归属。
- **Cloud session**：桌面端访问云 API 的短期凭据；与模型供应商凭据分离。桌面凭据落地方式需评估操作系统凭据库支持情况。
- **Provider credentials**：托管模型密钥只在云服务侧存取；BYOK 凭据继续走现有本地渠道配置和安全边界。
- **Payment credentials**：商户私钥仅由云服务运行环境的秘密管理方式提供，绝不进入客户端或仓库。

本地 API 与云 API 使用不同 host/base URL、认证中间件、配置、数据库连接、部署单元和发布门禁。不可通过公开桌面 loopback API、共享本地 owner token 或复用桌面 launch token 实现云认证。

## 3. 云服务模块

| 模块 | 责任 | 写入权威 |
| --- | --- | --- |
| `identity` | 微信 OAuth 会话、provider identity 绑定、云会话与撤销 | identity、登录会话 |
| `catalog` | 可用模型、商品和展示元数据 | 发布后的目录版本 |
| `pricing` | 商品定价、模型价格、额度换算和计量规则 | 生效中的版本化价格规则 |
| `payment` | 创建订单、支付方式适配、通知验签、退款与对账 | 订单和支付事件；不直接改余额 |
| `ledger` | 额度入账、预留、消费、释放、退款/冲正及授权调整 | 不可变账本分录；余额为派生/事务维护视图 |
| `modelgateway` | 用户/模型权限、供应商路由、密钥访问和请求代理 | 云任务及上游调用关联 |
| `usage` | 实际用量采集、费用核算、结算协调 | 已确认的用量及结算记录 |
| `operations` | 审计查询、对账、运营动作、健康与指标 | 操作审计，不承载业务余额规则 |

模块经应用层接口调用。Payment 不允许绕过 Ledger 直接更新余额；Gateway 不自行实现价格规则；HTTP handler 不直接访问数据库或供应商 SDK。

## 4. 关键业务流

### 微信扫码登录

1. Desktop 请求创建一次性 login session。
2. Cloud 创建高熵随机 state、过期时间和短期轮询凭据，返回 QR/授权 URL。
3. 用户在微信授权页面确认，微信把临时授权结果回调 Cloud。
4. Cloud 校验 state、应用/回调配置和授权码，完成身份映射；授权码一次性消费。
5. Desktop 轮询获得完成状态并交换最小权限云会话；服务端使轮询凭据失效。
6. 过期、取消、拒绝、撤销均明确返回；重复回调不重复创建账号或会话。

桌面端不直接兑换微信授权码，不保存 AppSecret；具体回调与二维码形态取决于已审核的微信开放平台产品。

### 充值与入账

1. 客户端请求商品目录；金额、币种和额度由云端返回。
2. 创建订单时服务端冻结商品版本、单价、币种、额度数量和账号归属。
3. 服务端调用选定的支付适配器，返回支付参数/链接。
4. 支付通知到达后，适配器验证签名和商户身份；Payment 校验金额、币种、订单状态。
5. 在数据库事务中记录唯一支付事件、转换订单并调用 Ledger 入账；重复通知返回相同结果。
6. 客户端查询订单及账本汇总，不以浏览器跳转、截图或客户端回执入账。

### 托管模型调用

1. Cloud 验证会话、账号状态、模型权限及请求大小/业务限制。
2. Pricing 依据模型、参数与供应商合同计算估价或费用上限。
3. Ledger 原子预留额度；不足则拒绝提交。
4. Gateway 选择协议实现并以服务端凭据调用上游，持久化云任务和幂等键。
5. Usage 记录供应商返回用量；Ledger 结算实耗并释放余额，失败/取消依规则释放或部分结算。
6. Desktop 通过云 API 查询任务结果；本地画布只把用户明确选定的结果导入本地。

## 5. 数据一致性原则

- 支付通知、退款通知、客户端创建请求、模型提交和结算均需稳定幂等键及唯一约束。
- 订单、支付事件和额度分录要能关联；外部副作用无法参与数据库事务时采用持久事件/待处理状态和可重放处理，不能先宣称成功再补账。
- Ledger 分录作为审计依据不可就地改写；纠正用反向分录/冲正记录。是否维护余额缓存由实现决定，但必须能校验重算一致性。
- 模型任务的请求状态、供应商状态、额度预留和实际结算分开记录，不能把一次 HTTP 断线直接视为上游失败。
- 云服务失效不阻断本地功能；客户端不把未确认云写入标成成功。

## 6. 部署与演进

- 一个云服务应用单元、一个受控云数据库和独立秘密管理配置作为首期方向；数据库产品、地域、容灾等级、队列与对象存储尚待运维决策。
- 微信回调、支付通知和 Cloud API 只在 HTTPS 公网域名上开放；桌面本地 API 不公开。
- 沙箱、测试和生产使用不同应用、密钥、数据库和支付商户配置；禁止跨环境复用真实凭据。
- 当模型网关需要独立扩缩容、支付隔离或独立故障域成为实际需求时，再依据现有模块接口拆分服务；客户端 API 尽量保持稳定。

## 7. 需要共同确认

1. 云服务是否确定为独立 Go 服务/独立部署，而不是新增仓库或部署到已有后端？
2. 目前可用的云主机、域名、数据库和密钥管理方式是什么？
3. 微信应用类型/审核状态和支付宝商户产品是哪一种？
4. 首期模型目录、单用户及单任务成本上限如何定？
5. 用户额度是否过期、是否支持退款、供应商失败时的成本由谁承担？
