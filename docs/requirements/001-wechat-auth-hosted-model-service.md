## 1. 背景与问题

LuckyTV 当前是单用户、本地优先桌面工作区。`docs/content/docs/backend/code-map.mdx` 明确说明本地后端不提供登录、注册、计费、支付、公开分享或云存储路由。`backend/internal/workspace/service.go` 的 workspace owner 是本机数据身份，不应充当云账号。

仓库仍有 `backend/internal/luckytv/` 及对应前端连接/余额界面，用于适配旧云服务的设备授权、模型目录和充值协议；这些代码不是自有账号、支付或账务后端，且 `backend/internal/luckytv/origin.go` 已禁用旧生产源 `https://luckytv.app`。不得把旧客户端转发接口误认为已有可运营的云服务。

产品方向：提供可选的好运TV云服务，将账号、额度/账本、支付和托管模型网关部署为一个模块化单体；桌面端继续保有本地创作与用户自带 Key（BYOK）能力。此架构方向来自用户讨论，具体供应商、额度规则、部署条件仍待决策。

## 2. 目标与非目标

### 目标

- 支持用户通过微信扫码建立好运TV云账号会话；邮箱登录/找回方式按决策确定。
- 在同一可部署云服务内提供账号、额度账本、支付订单和托管模型网关模块，模块职责与数据权限清晰。
- 允许已登录用户购买好运TV服务额度，并在调用托管模型时由服务端校验和结算额度。
- 保持桌面本地 workspace 身份与云账号分离；云服务不可用时，本地工作区与 BYOK 流程仍可使用。
- 支付、账本和模型结算具备幂等、审计和对账路径。

### 非目标

- 不把本地 SQLite workspace 改造成多租户云数据库，也不因登录而迁移或上传本地项目。
- 不把微信 AppSecret、支付宝私钥或模型供应商密钥打包进桌面客户端。
- 首期不拆微服务；内部采用模块化单体，部署一个服务进程/应用单元。
- 不默认开发订阅、自动续费、插件购买或技能权益；首期额度范围需决策。
- 不删除或重写已有历史数据、用户自带模型渠道和插件扩展能力。

## 3. 用户场景与需求

- 作为桌面端用户，我可以选择微信扫码登录云服务，且取消/过期/网络失败不影响本地工作区。
- 作为云服务用户，我可以查看服务端权威额度、选择商品并发起支付；客户端不得自行确认到账。
- 作为购买了托管模型额度的用户，我可以调用服务端允许的模型；额度不足、模型不可用或结算失败时得到明确状态，不能绕过服务端扣费。
- 作为 BYOK 用户，即使没有登录云服务，仍可配置自有模型渠道并继续本地创作。

## 4. 范围与边界

- 客户端：账户入口、扫码/轮询状态、云账号会话安全存储、商品/订单/额度展示、托管模型请求配置；本地 workspace 和 BYOK 继续独立。
- 云服务：账号身份与会话、微信 OAuth 回调、额度商品、订单、支付回调、账本、模型目录/定价、托管代理、用量计量、退款/冲正、管理审计与对账接口。
- 当前本地 Go API 与未来云 API 必须具有不同的部署配置、数据目录/数据库、认证机制和服务边界；不得通过开放本地 loopback API 充当公网云 API。
- 微信身份只关联云账号，不决定本地 SQLite/IndexedDB 数据归属。
- 云服务可先作为单独的 Go 服务部署，与本地后端分离；是否复用现有 Go 模块、数据库及运维栈待架构验证。
- 自营托管模型的请求和密钥只经过云服务；BYOK 请求保持既有客户端/本地后端路径，不应被静默改道。

## 5. 验收标准

### 账号与会话

- [ ] 微信扫码登录使用服务端发起/完成的授权流程；服务端校验一次性 state、回调来源与授权结果，客户端不接触 AppSecret。
- [ ] 登录二维码会话有过期、取消、已使用和轮询频控语义；重放或伪造状态不能登录。
- [ ] 会话可安全刷新、主动退出和撤销；日志、诊断包与客户端持久化不暴露密钥或完整敏感凭据。
- [ ] 云账号与本地 workspace owner 相互独立；未登录或云服务不可用时本地项目可正常打开和保存。
- [ ] 邮箱登录、账号绑定、解绑和找回的范围按决策实现，不擅自合并同邮箱/微信身份。

### 支付与额度

- [ ] 商品价格、币种、额度数量和有效期由服务端提供并校验，客户端提交价格不能决定入账值。
- [ ] 支付平台异步通知在服务端完成签名校验、商户/订单/金额核对与幂等处理；仅服务端确认后才增加额度。
- [ ] 重复通知、重复查询、客户端伪造成功、金额不匹配、超时订单和退款/冲正均有明确结果且不会重复入账。
- [ ] 额度账本可追溯充值、冻结/扣费、释放、退款及人工调整；余额可由账本重算或对账。
- [ ] 订单状态、账本变化和支付事件可以关联审计，不记录支付私钥、完整支付凭据或不必要个人信息。

### 托管模型

- [ ] 所有托管模型请求由云服务鉴权、执行额度准入、记录请求与计量结果；客户端不能访问上游密钥或绕过网关直接使用托管账号。
- [ ] 费用可预估时在提交前按服务端规则冻结/预留额度，结束后结算并释放余额；异步或费用未知的任务定义上限与最终结算策略。
- [ ] 请求超时、重复提交、供应商失败、取消、任务恢复和结算重试不会导致重复扣费或免费重复调用。
- [ ] 模型目录、可用权限、价格与扣费规则由服务端权威控制，客户端仅展示结果。
- [ ] BYOK 任务仍使用用户自己的配置和凭据，不误扣云额度；云网关与本地任务状态边界清楚。

### 运行与运维

- [ ] 云服务有健康检查、结构化脱敏日志、审计、指标、备份恢复、密钥轮换和支付/额度对账流程。
- [ ] 数据迁移可重复验证且具备备份与恢复演练；不能把本地开发数据库当生产账号或账务数据库。
- [ ] 端到端沙箱验证覆盖微信授权、支付回调、入账、托管模型计量、退款/冲正和服务故障；正式商户/生产验证需单独授权。

## 7. 技术方案

### 建议模块与数据流

桌面端申请云登录会话并显示服务端提供的二维码；微信回调在云服务完成 state 校验及身份绑定，桌面端轮询一次性会话结果，最终取得最小权限的好运TV云会话。云会话只用于云 API，不替换本地 workspace 身份。

云服务内部采用模块化单体，至少划分 `identity`、`catalog/pricing`、`payment/order`、`ledger`、`modelgateway/usage`、`audit` 责任。具体目录与 Go 包布局需在实现前按当前 Go 版本和依赖栈验证。模块可共用一个云数据库，但账务变化必须通过账本/领域服务，不允许各模块直接改余额字段。

支付流程：客户端请求创建订单 → 服务端从商品目录计算金额并保存待支付订单 → 调起已签约支付产品 → 支付平台向服务端异步通知 → 验签并核对商户、订单、金额与币种 → 幂等更新支付事件和账本 → 客户端查询服务端订单/余额。客户端回跳只用于刷新展示，不是入账证据。

托管生成流程：客户端向云网关提交请求 → 认证账号与模型权限 → 服务端按定价预留/校验额度 → 使用服务端密钥请求供应商 → 记录任务与实际用量 → 结算、释放或冲正额度 → 返回可查询的服务端任务状态。幂等键、超时、供应商重试与任务恢复规则需要在详细设计中明确。

### API / 数据 / 配置变更

- API：新增版本化云 API；不要直接把云服务合同塞进本地 workspace API。
- 数据库：新增云端 identity、session/device authorization、product/price、payment order/event、ledger entry、usage/task、audit 结构；仅追加迁移版本。
- 配置：微信 OAuth、支付宝商户、模型供应商密钥通过云端 secret 管理注入；开发/沙箱/生产隔离。不得将真实值提交仓库或发送到客户端。
- 桌面存储：云会话凭据需采用当前平台安全存储或受限凭据文件方案，选型待验证；不得与模型 API Key 混为同一身份。
- 文档：同步 API/OpenAPI、数据库、部署、安全、账号与支付说明；更新现有旧连接 UI/接口的退役或迁移策略。

### 失败、权限和恢复

- 所有云 API 服务端鉴权并校验账号、订单、任务和账本归属；客户端 UI 隐藏不是授权控制。
- OAuth state、授权码、支付回调和幂等键均限制有效期、作用域和重放；错误响应不得泄露内部 URL、密钥或上游敏感报文。
- 账本写入与订单状态转换使用事务/唯一约束或等效一致性机制；外部支付回调通过持久事件和可重放处理实现可恢复。
- 模型供应商超时不能盲目重发不可幂等的付费请求；先按供应商能力定义幂等与查询恢复策略。
- 生产部署、域名 DNS/TLS、真实微信/支付宝回调、真实付费模型和退款均需单独授权并在沙箱验收后执行。

## 10. 风险与开放问题

- 微信开放平台主体、应用审核、回调域名和账号绑定规则可能决定可用登录流程；阶段 0 未完成前不应写真实 OAuth 集成。
- 支付产品、商户资质、回调网络可达性、退款与对账规则未确认；不要假设任意支付宝支付方式可用。
- 额度与实际模型成本存在差异，需定义定价、汇率/成本变化、单次上限、冻结与退款/冲正，避免先扣后无法解释。
- 云端账号与本地 workspace 若错误耦合，可能造成本地数据不可用、跨账号泄露或误迁移；必须保持隔离并测试云服务离线降级。
- 服务端托管模型网关涉及密钥保管、滥用、供应商条款、内容安全与成本超支；须先确定限流、配额、日志留存和人工处置责任。
- 现有旧账号/充值 UI 依赖停用的旧云服务；迁移时要避免误导用户显示可用状态，并明确旧凭据和待处理订单的兼容/清理策略。
