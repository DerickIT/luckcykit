# 001 微信登录与托管模型服务

- 状态：讨论稿 v2（方案待共同确认；未授权实施生产集成）
- 创建：2026-11-18；本次整理：2026-11-19
- 相关文档：[架构方案](../architecture/cloud-service.md) · [技术设计](../technical/cloud-service.md) · [Skills 设计](../skills/cloud-service-skills.md)

## 一句话目标

在不改变本地工作区所有权和 BYOK 使用方式的前提下，增加一个可选的好运TV云服务：微信登录、购买服务额度、调用托管模型；首期作为一个可独立部署的模块化单体，而非微服务群。

## 当前事实

- LuckyTV 是单用户、本地优先桌面工作区；本地 workspace owner 是本机数据身份，不是互联网账号。见 `backend/internal/workspace/service.go`。
- 当前本地 API 不等同于云 SaaS API；代码地图明确没有云登录/支付/计费路由。
- `backend/internal/luckytv/` 和账户余额界面是旧云服务的客户端适配，并非自有 OAuth、支付回调或账本实现。旧生产源已由 `backend/internal/luckytv/origin.go` 禁用。
- 模型 Provider/Protocol、自定义渠道、插件和 BYOK 是当前本地产品能力，应继续保留。

## 用户与核心场景

1. 本地创作者不登录也可打开、保存本地项目并使用 BYOK。
2. 需要好运TV托管算力的用户，可选择微信登录、查看额度并使用授权模型。
3. 用户购买额度后，支付到账以云端验证的支付通知和账本为准，客户端仅显示状态。
4. 云服务不可用、登录过期或用户退出时，本地创作不被锁定，也不上传本地项目。

## 产品范围

**首期目标范围**：云账号/会话、微信扫码登录、服务端模型目录与托管网关、额度账本、支付宝充值（完成商户与产品确认后）、订单查询、退款/冲正和必要的运营对账。

**客户端范围**：登录/退出、账号与额度展示、商品/订单入口、托管模型选择与任务状态；本地身份、项目和 BYOK 独立存在。

**明确不包含**：把本地 SQLite 改成多租户云数据面；强制登录才能使用本地能力；把云端密钥放入客户端；首期拆微服务；未经讨论增加订阅、自动续费、插件/技能售卖、团队协作或项目云同步。

## 核心需求与验收

### 身份

- [ ] OAuth 由服务端发起和完成；校验一次性 `state`、过期和回调结果，客户端不得持有微信 AppSecret。
- [ ] 登录会话支持待扫码、已确认、拒绝/取消、过期、完成及撤销；授权码不可重放。
- [ ] 桌面云会话只用于云 API；本地 workspace owner 不变，云端故障时本地读写和 BYOK 可用。
- [ ] 邮箱备用登录、找回、微信绑定/解绑以及账号合并规则先决策，不按相同邮箱自动合并。

### 支付和账本

- [ ] 商品、价格、币种、额度和有效期由服务端权威提供，客户端不能指定入账金额。
- [ ] 服务端验签并核对商户、订单、金额和币种；仅验证成功的支付事件可幂等入账，客户端跳转回调不是到账凭证。
- [ ] 账本可追溯充值、额度预留、消费、释放、退款/冲正及授权调整；重复通知和重试不会重复入账。
- [ ] 订单、支付事件与账本变更可关联查询和对账；退款后额度不足时的负余额/冻结规则先决策。

### 托管模型

- [ ] 托管调用只能由云端鉴权并代理供应商请求，供应商凭据留在服务端；模型目录、权限和价格以服务端为准。
- [ ] 请求前依服务端价格预留额度，完成后按实际用量结算并释放差额；无法预估的异步任务要有用户可见上限。
- [ ] 重试、断线恢复、取消和供应商超时须定义是否重发；不得因状态不明自动重复提交可能收费的请求。
- [ ] BYOK 与托管调用路径清晰区分，不误用云凭据或扣减云额度。

## 主要风险与上线门槛

- 微信主体、网站应用审核、回调域名/备案尚待确认。
- 支付宝商户签约产品及退款/对账能力尚待确认，不能据此编写生产回调实现。
- 额度售价与供应商成本可能变化，需要单次上限、预留/结算与争议处理规则。
- 云身份与本地 workspace 混淆会造成锁定本地数据或越权，必须通过离线/BYOK验收。
- 旧账户/充值 UI 可能仍呈现旧服务概念，迁移前须决定退役、替换或暂时隐藏策略。
- 真实支付、退款、生产 OAuth、生产模型密钥和对外部署均需独立授权；先完成沙箱与恢复演练。

## 分阶段交付

1. **共同定稿：** 确认上表决策，形成威胁模型、额度不变量、成本/限额模型、数据流和 API 草案。
2. **云服务骨架与身份：** 云/本地边界、独立配置/迁移/部署、审计基础；实现 OAuth 沙箱与桌面离线行为。
3. **支付与账本：** 商品、订单状态机、幂等账本和单一已签约产品沙箱，完成退款/对账路径。
4. **托管模型：** 模型授权、凭据管理、额度预留/结算、任务查询与安全恢复；BYOK 保持原路径。
5. **试点验收：** 演练故障、备份恢复、账务对账、滥用与成本限制；生产开通另行确认。

## 当前状态

目前已有需求/架构准备，以及独立云服务的本地沙箱纵向切片；没有自有云账号的生产 OAuth、支付账本生产流程或托管模型服务。没有微信/支付宝真实凭据，也未连接任何商户或生产模型。现有事实已依据本地代码地图、workspace 与 luckytv origin 实现核对。

## 沙箱一期实施记录

- 已确认范围：本仓库内独立 Go 命令与数据边界；沙箱额度为无现金等值的整数点数。沙箱数据库为独立 SQLite 文件，仅用于开发/测试，不代表生产数据库选型。
- 入口：`cd backend && LUCKYTV_CLOUD_SANDBOX=true go run ./cmd/cloud`；默认监听 `127.0.0.1:8081`，默认数据目录为 Git 忽略的 `.local/cloud-service-sandbox`。
- 沙箱 API：`GET /api/v1/products`、`POST /api/v1/sandbox/login`、`POST /api/v1/orders`、`POST /api/v1/orders/{id}/sandbox-payment`、`GET /api/v1/orders`、`GET /api/v1/ledger`、`GET /api/v1/account`、`POST /api/v1/sessions/revoke`。需登录的端点使用 `Authorization: Bearer <token>`；模拟入账还要求 loopback 请求及 `Idempotency-Key`。
- 商品标识和点数由服务端沙箱目录提供；订单保存商品与点数快照。重复的同账号/订单幂等请求回读原支付结果；账本与支付事件、订单状态同事务提交，余额从追加式账本汇总。
- 沙箱关闭时，不挂载模拟登录、商品和模拟支付路由，也不初始化沙箱目录；当前运行时拒绝 production 环境和非 loopback 监听。未建设前端；本地 workspace、owner、BYOK 与旧 LuckyTV 连接路径未接入云服务。
- 验证：云服务聚焦测试 `go test ./internal/cloud/... ./cmd/cloud/...` 通过（32 个顶层用例；含子测试 40 项）；`go list -deps` 未发现依赖本地 `internal/app`、`internal/bootstrap` 或 `internal/database`；`node scripts/deadcode-budget.mjs` 通过（647 项，基线 647）。结构预算在聚焦校验修复后通过（`backend/internal/app` 9,359 行，基线 9,365 行）。完整 `go test ./...` 在当前 Windows 环境失败（3,757 项通过、207 项失败、63 项跳过），主要涉及缺少 `/bin/sh`、`ffprobe`/桌面外部 CLI 及临时目录清理；云模块聚焦测试独立通过。`git diff --check` 通过。真实微信 OAuth、真实支付/退款、托管模型、生产数据库/部署和生产密钥仍需后续决策及独立授权。
