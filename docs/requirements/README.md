# 需求记录

本目录记录需要跨阶段追踪的产品需求、技术方案和验收证据。它是开发过程记录，不替代代码、配置、测试、API 规范或正式产品文档。

## 何时建立记录

建议为以下事项建立独立需求记录：跨多个模块或迭代的功能、用户可见行为变化、外部服务或插件协议变化、持久化/数据库/API 合同变化、身份与权限、支付计费、密钥与安全、删除/迁移/导入导出，以及需要产品决策的工作。

单文件小修、纯拼写修正和无需跨阶段追踪的低风险改动，可直接通过 Issue/PR 描述记录，不必为了流程创建文件。

## 文件命名与状态

- 使用 `NNN-short-kebab-case.md`，编号在本目录内递增，例如 `001-local-sign-in.md`。
- 复制 [`template.md`](template.md) 后填写；未确认的信息标为“待确认”，不得编造已决策事实。
- 状态使用：`草拟`、`待决策`、`已批准`、`实施中`、`已验证`、`已完成`、`已取消`。
- 只有验收项全部有证据时标为“已完成”；局部实现可标为“实施中”并注明未完成项。
- 需求变更追加到“变更记录”，保留原始目标和决策脉络，不删除过时结论而不留说明。
- 不记录密码、Token、Cookie、真实 API Key、个人敏感信息、客户资料、内部授权凭据或不宜入库的线上数据。需要证据时使用脱敏摘要、测试名称、提交引用或安全存储位置说明。

## 记录质量

- 目标描述用户价值和问题，不以某种实现方案冒充需求。
- 范围明确写出包含与不包含；将假设与已确认决策分开。
- 验收标准采用可观察、可复现的行为，覆盖正常、失败、权限、边界和恢复场景。
- 技术方案说明权威数据源、模块边界、API/数据变更、错误与安全、迁移和回滚策略。
- 任务拆分需能独立验证；记录实际执行的验证及结果，不预先填成功结果。
- 对支付、账务、身份、权限、密钥、不可逆删除和生产数据操作，必须有明确授权边界、幂等/审计策略和人工验收要求。

## 与其他记录的关系

- 即时问题和讨论放在项目现用的 Issue / PR /任务系统中；需求文件记录稳定目标、决策和验收，不复制整段讨论。
- API 合同以代码、OpenAPI 和对应 API 文档为准；数据库状态以迁移和数据库文档为准。
- 架构决定可在需求文件中记录理由；若需要长期独立查阅，可新增轻量 ADR，并从本文件或需求记录链接过去。
- 发布说明和用户指南写入产品文档，不用本目录代替公开文档。
